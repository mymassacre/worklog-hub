# worklog-hub

Небольшой локальный сборщик фактически списанного рабочего времени. Он читает
GitLab timelogs через GraphQL API; для Jira Server/Data Center добавлен
экспериментальный адаптер REST API v2. Данные приводятся к общей модели и
сохраняются в SQLite. Проект ничего не записывает в GitLab или Jira.

## Что уже есть

- GitLab GraphQL `/api/graphql`: проверка подключения и cursor-пагинация;
- фильтр по включительному диапазону фактических дат;
- группы и их иерархия, проекты, пользователи и членство;
- issues, tasks, merge requests, ветки, итерации и эпики;
- повторяемый UPSERT без дублей;
- явный список интересующих групп в TOML-конфиге;
- токен в системном keyring (в Windows — Credential Manager);
- сверка периода в выбранных группах: исчезнувшие записи удаляются из SQLite;
- полная сверка каталога: исчезнувшие сущности помечаются `is_active = 0`;
- журнал успешных и неуспешных запусков;
- экспериментальный `JiraCollector` для штатного Server/Data Center REST API v2;
- предварительные связи с Jira по ключам вида `ABC-123` в заголовке или ветке.
- локальный маппинг проектов, задач и пользователей: предложения и ручное подтверждение.

## Установка

Нужен Python 3.12 или новее. Для хранения токена используется библиотека `keyring`.

```powershell
py -3.12 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -e .
```

Скопируйте пример в локальный конфиг:

```powershell
Copy-Item worklog-hub.example.toml worklog-hub.toml
```

В `worklog-hub.toml` задайте свой сервер и полные пути групп из их URL:

```toml
[database]
path = "worklog-hub.sqlite3"

[gitlab]
url = "https://gitlab.example.com"
groups = ["company/team", "another-group"]
include_subgroups = true
timeout_seconds = 30
```

Для первого подключения можно указать `groups = []` или пока не задавать это поле.
Сохраните токен командой `worklog-hub gitlab login`, затем посмотрите доступные группы:

```powershell
worklog-hub gitlab groups
worklog-hub gitlab groups --search backend
```

Команда выводит полные пути, названия, ID и URL всех видимых пользователю токена
групп (включая публичные), независимо от текущего списка в конфиге. Получает все
страницы ответа. Она не записывает ничего в SQLite или конфиг. Выберите нужные
пути из вывода и внесите их в `gitlab.groups`.

Для `check` и `sync` `groups` — обязательный непустой список. `company/team` — полный путь группы,
не её отображаемое название, URL или числовой ID. При `include_subgroups = true`
собираются также доступные вложенные группы и их проекты. При `false` — только
перечисленные группы и непосредственно принадлежащие им проекты. Пересекающиеся
группы и проекты не создают дублей. Shared-проекты, принадлежащие другой группе,
не включаются. Архивные проекты выбранных групп включаются.

Группа — контейнер проектов и подгрупп. Эпик принадлежит группе и может объединять
задачи нескольких проектов. Поэтому это не цепочка «группа → проект → эпик»:
проекты и эпики находятся в группе, задачи — в проектах.

Путь SQLite считается относительно каталога конфига, а не текущей рабочей папки.
По умолчанию программа ищет `worklog-hub.toml` в текущей папке; другой конфиг
указывается перед командой: `worklog-hub --config C:\path\app.toml gitlab check`.
Локальный `worklog-hub.toml` исключён из Git. Если выбрано другое имя, его нужно
самостоятельно исключить из Git при необходимости.

Один раз сохраните токен из интерактивного терминала:

```powershell
worklog-hub gitlab login
```

Команда запросит токен со скрытым вводом и сохранит его в системном хранилище.
Повторный `login` заменит токен для того же сервера. Запись привязана к URL GitLab
и текущему пользователю ОС (service: `worklog-hub/gitlab`, account: URL сервера).
В Windows используется непосредственно Windows Credential Manager. На macOS/Linux
поддерживаются системные Keychain, Secret Service и KWallet. Если безопасного
хранилища нет, команда завершится ошибкой; файловый fallback не применяется.
Токен не передаётся аргументом команды, не записывается в конфиг, SQLite или журнал.

Токену нужны права чтения выбранных групп, проектов и timelogs; обычно используется
PAT с `read_api`. Фактическая доступность сущностей зависит от прав его пользователя.
Переменные `GITLAB_URL`, `GITLAB_TOKEN`, `GITLAB_TIMEOUT_SECONDS`, `WORKLOG_DB_PATH`
больше не используются; `.env` не читается. Сначала перенесите URL и настройки в
TOML и выполните `login`, затем удалите старые секреты из своего способа запуска.

## Команды

```powershell
worklog-hub gitlab check
worklog-hub gitlab sync --from 2026-10-01 --to 2026-10-31
worklog-hub sync-status
```

Диапазон `--from` / `--to` включительный. `spent_at` хранится в UTC, а исходная
календарная дата списания — отдельно в `spent_date`.

Команда `check` проверяет пользователя токена и доступность выбранных групп.
Отсутствующая или недоступная группа останавливает синхронизацию; перехода к
сбору всех доступных групп при ошибке конфига нет.

Команда `gitlab sync` получает каталог выбранных групп, затем запрашивает timelogs
по каждому входящему в них проекту с `projectId`. Сохраняются отдельные списания
по задачам и merge requests, не агрегированные `time_stats`. Сбор списаний
непосредственно по эпикам этим адаптером пока не реализован. Итерации и каталог
эпиков зависят от редакции, лицензии и версии конкретного GitLab.

Каталог хранится в таблицах `groups`, `projects`, `users`, `memberships`,
`work_items`, `branches` и `iterations`. Issues, tasks, merge requests и эпики
используют общую таблицу `work_items` с различным значением `kind`. Исходный JSON
сохраняется для групп, проектов, пользователей, членства, work items и итераций.

## Повторная сверка

Сначала клиент полностью получает все страницы заданного периода. Только после
успеха данные записываются транзакцией, а локальные GitLab-записи, которых больше
нет в полной выборке этого периода в выбранных группах, удаляются. Ошибка сети или пагинации не
удаляет ранее загруженные данные.

Каталог также загружается со всей пагинацией. При успешной полной загрузке
сущности выбранной области, которых больше нет в доступной выборке, не удаляются физически, а
помечаются неактивными. Это сохраняет историю и внешние связи.

Изменение списка групп не удаляет и не деактивирует данные за пределами новой
области. Ранее загруженная история других групп остаётся в SQLite: это не
автоматическая очистка базы. Пользователи общие для разных групп, поэтому
их отсутствие в ограниченной выборке не деактивирует их глобально.
Для отдельного GitLab-сервера используйте отдельный файл SQLite.

Если отдельный тип каталога недоступен из-за роли пользователя, лицензии или
версии GitLab, синхронизация продолжает работу и записывает предупреждение.
Такой раздел считается неполным: ранее сохранённые строки этого типа не
помечаются неактивными. Ошибки подключения, авторизации самого токена и
пагинации остаются фатальными.

## Jira

Реализован экспериментальный адаптер **штатного Jira Server/Data Center REST API
v2** с Personal Access Token (PAT). Основания: официальная документация REST API
Jira 9.12.2 и аннотации/сигнатуры REST-компонентов официального образа Jira
10.3.9. Поведение веб-клиента рабочей Jira, её версия и плагины пока неизвестны.
Успешное чтение worklog с лицензированного стенда или рабочего сервера ещё
не проверялось. Локальные тесты используют синтетические ответы API.

В конфиг добавьте секцию (можно использовать Jira без секции GitLab):

```toml
[jira]
url = "https://jira.example.com" # При наличии context path: https://host/jira
projects = []                  # После просмотра списка: ["ABC", "TEAM"]
timeout_seconds = 30
```

```powershell
uv run worklog-hub jira login
uv run worklog-hub jira check
uv run worklog-hub jira projects
# Внесите нужные ключи в jira.projects, затем:
uv run worklog-hub jira sync --from 2026-10-01 --to 2026-10-31
```

PAT хранится отдельно от GitLab в системном keyring: service `worklog-hub/jira`,
account — URL Jira. Клиент отправляет `Authorization: Bearer <PAT>`. Это не
поддержка произвольного токена браузерной сессии, Cookie или Jira Cloud API token.
`login` только сохраняет токен, `check` проверяет его чтением текущего пользователя.
`login`, `check` и `projects` не требуют списка выбранных проектов; `sync` требует
непустой список. Все сетевые операции адаптера — GET, записи в Jira нет.
Для другого сервера Jira используйте отдельную SQLite: попытка сменить URL
уже сохранённого источника завершается ошибкой, чтобы не смешать одинаковые ID.

| Операция | REST-маршрут |
| --- | --- |
| Проверка PAT | `GET /rest/api/2/myself` |
| Доступные проекты | `GET /rest/api/2/project` |
| Проверка выбранного проекта | `GET /rest/api/2/project/{key}` |
| Задачи выбранных проектов | `GET /rest/api/2/search`, JQL `project IN (...) ORDER BY key ASC`, `startAt` / `maxResults` |
| Отдельные списания задачи | `GET /rest/api/2/issue/{id}/worklog` |

Собираются проекты, задачи (включая эпики и подзадачи) и авторы списаний.
Типы `Epic`/`Эпик` распознаются по штатному названию; нестандартные переименованные
типы сохраняются как обычные задачи, исходный `issuetype` остаётся в JSON.
Членство, полная выгрузка пользователей и Jira Agile boards/sprints этим адаптером
пока не собираются. Связи GitLab с Jira по ключам остаются предварительными.

Фактическая дата — `worklog.started`, длительность — `timeSpentSeconds`.
`spent_at` приводится к UTC, `spent_date` сохраняет дату исходного `started`.
`created` и `updated` не подменяют дату работы. Фильтр периода включительный.

Для полноты адаптер обходит **все видимые задачи выбранных проектов**, получает
их списания и фильтрует период локально. На больших проектах это может быть
дорого. JQL-фильтр только по `worklogDate` не используется, поскольку не даёт
надёжной сверки изменённых/перенесённых записей. Пагинация поиска проверяется:
изменившийся `total`, повтор задач или неправильный `startAt` останавливают запуск.
Worklog-метод в проверенной Jira 10.3.9 не принимает параметры пагинации и
возвращает полный список. Если `total` не совпадает с числом записей либо
`startAt != 0`, запуск останавливается без сохранения полученной выборки.

**Исчезнувшие Jira-записи не удаляются и не деактивируются автоматически.** API
может скрывать списания из-за прав или скрытого поля Log work: пустой ответ не
доказывает удаление. Повторный sync обновляет существующие записи по ID и
добавляет новые, сохраняя прежнюю историю. Ошибка получения хотя бы одной задачи
или её списаний останавливает загрузку до записи каталога/списаний в SQLite;
ошибка фиксируется в журнале запусков. Транзакции записи каталога и списаний
остаются отдельными, как в общем механизме синхронизации.

Редиректы (включая SSO) блокируются до пересылки PAT. HTML вместо JSON, HTTP
401/403/404 и ошибки схемы считаются ошибками, а не пустыми выборками. При
запрещённом REST API адаптер не пытается обходить запрет через другие URL или
браузерные Cookie. Сам факт доступности веб-клиента не доказывает доступность PAT.

Источники: [REST API Jira 9.12.2](https://docs.atlassian.com/software/jira/docs/api/REST/9.12.2/),
[PAT в Data Center](https://confluence.atlassian.com/enterprise/using-personal-access-tokens-1026032365.html).
Локальный исследовательский стенд и границы его проверки описаны в
[tools/jira-lab/README.md](tools/jira-lab/README.md).

## Связи GitLab ↔ Jira

Маппинг хранит соответствия между **уже загруженными** сущностями. Он работает
только с локальной SQLite, не обращается к API и не требует keyring. Сначала
выполните синхронизацию обеих систем в одну БД. `gitlab groups` и `jira projects`
показывают удалённые справочники, но сами по себе не сохраняют их в SQLite.

| Тип | Правило |
| --- | --- |
| `project` | Репозиторий GitLab ↔ проект Jira; вручную, допускаются многие-ко-многим. |
| `task` | Issue/task/MR GitLab ↔ задача/эпик Jira; допускаются многие-ко-многим. Связь означает связанную работу, а не доказательство идентичности объектов. |
| `user` | Аккаунт GitLab ↔ аккаунт Jira; подтверждённые связи один-к-одному. Одинаковые имена и логины не доказывают, что это один человек. |

Связи не изменяют исходные ID, записи worklog, даты или суммы часов и не создают
задач в удалённых системах. Повторные списания между Jira и GitLab автоматически
не объединяются: для расчёта итогов потребуется отдельно определить источник
часов и правило исключения дублей.

### 1. Посмотреть загруженные сущности

```powershell
uv run worklog-hub mapping entities project --source gitlab
uv run worklog-hub mapping entities project --source jira
uv run worklog-hub mapping entities user --source gitlab
uv run worklog-hub mapping entities user --source jira
uv run worklog-hub mapping entities task --source gitlab
uv run worklog-hub mapping entities task --source jira
```

Вывод содержит селектор, название, внешний ID и признак активности. В Jira
пользователи пока собираются только из авторов worklog. Для GitLab `project` —
репозиторий, а не группа: для группы свяжите каждый нужный репозиторий.

### 2. Задать известные соответствия

Подставьте свои селекторы из предыдущего вывода:

```powershell
uv run worklog-hub mapping link project --gitlab "team/backend" --jira ABC
uv run worklog-hub mapping link project --gitlab "team/frontend" --jira ABC
uv run worklog-hub mapping link user --gitlab ivanov --jira i.ivanov
```

`link` сразу сохраняет **подтверждённую** ручную связь. Повтор команды для той же
пары не создаёт дубликат связи. При одинаковых логинах/селекторах разных сущностей
команда останавливается; используйте точный внешний ID из `mapping entities`.
Связать неактивную сущность нельзя. Новая связь аккаунта с другим аккаунтом
потребует сначала отклонить прежнюю подтверждённую связь через `mapping reject`.

Можно явно связать задачу или MR, даже без автопоиска и соответствия проектов:

```powershell
uv run worklog-hub mapping link task --gitlab "team/backend#12" --jira ABC-123
uv run worklog-hub mapping link task --gitlab "team/backend!34" --jira ABC-123
```

Для задач также принимается точный `web_url` или внешний ID. Селектор `#12`
обозначает issue/task, `!34` — merge request; номер без полного пути проекта
не используется, потому что он повторяется в разных репозиториях.

### 3. Найти и проверить предложения

```powershell
uv run worklog-hub mapping suggest
uv run worklog-hub mapping list --status proposed
# Вместо 12 укажите ID конкретной связи из mapping list:
uv run worklog-hub mapping confirm 12
uv run worklog-hub mapping reject 12
uv run worklog-hub mapping list --status confirmed
```

Можно ограничить поиск: `mapping suggest --kind task` или `--kind user`.
Просмотр: `mapping list --kind project|task|user` с необязательным `--status`.

Предложения задач строятся по ключам реально загруженных задач Jira в заголовке,
описании и ветке GitLab, **только внутри подтверждённых активных пар проектов**.
Это исключает догадки по похожим названиям. Для групповых эпиков GitLab без
проекта автопоиск не выполняется; их можно связать вручную по внешнему ID/URL.
Совпавшие логины аккаунтов дают только предложения пользователей, не автосвязь.

Статусы: `proposed` — предложена, `confirmed` — подтверждена, `rejected` — отклонена.
Повторный поиск и синхронизация сохраняют решения пользователя. Устаревшие
подсказки остаются видимыми с `Актуальна=0`: исчезнувший ключ, неактивная сущность
или отменённое соответствие проектов не позволяют подтвердить предложение.
После обновления данных повторите `mapping suggest`. Подтверждённая связь сама
по себе не отменяется при изменении заголовка; отменить её можно через `reject`.

Связи находятся в `entity_mappings`, история решений — в `mapping_reviews`.
Старая таблица `entity_links` остаётся журналом найденных ключей; она не содержит
проверенных соответствий и не заменяет новый маппинг. Миграция `004` добавляет
новые таблицы при первом обращении к БД, сохраняя ранее загруженные данные.
