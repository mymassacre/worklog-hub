# worklog-hub

Небольшой локальный сборщик фактически списанного рабочего времени. На первом
этапе он читает timelogs и связанный каталог сущностей из штатного GitLab
GraphQL API, приводит их к общей модели и сохраняет в SQLite. Проект ничего не
записывает в GitLab.

## Что уже есть

- GitLab GraphQL `/api/graphql`: проверка подключения и cursor-пагинация;
- фильтр по включительному диапазону фактических дат;
- группы и их иерархия, проекты, пользователи и членство;
- issues, tasks, merge requests, ветки, итерации и эпики;
- повторяемый UPSERT без дублей;
- полная сверка периода: исчезнувшие из успешной выборки записи удаляются из SQLite;
- полная сверка каталога: исчезнувшие сущности помечаются `is_active = 0`;
- журнал успешных и неуспешных запусков;
- заготовка `JiraCollector` без сетевых запросов;
- предварительные связи с Jira по ключам вида `ABC-123` в заголовке или ветке.

## Установка

Нужен Python 3.12 или новее. Сторонних runtime-зависимостей нет.

```powershell
py -3.12 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -e .
```

Задайте переменные окружения. Настоящий `.env` проект не читает и не создаёт:

```powershell
$env:GITLAB_URL = "https://gitlab.example.com"
$env:GITLAB_TOKEN = "ваш-токен"
$env:WORKLOG_DB_PATH = "worklog-hub.sqlite3" # необязательно
```

Токену нужны права на чтение видимых пользователю timelogs, групп, проектов и
их сущностей. Токены не сохраняются в SQLite и не выводятся в журнал.

## Команды

```powershell
worklog-hub gitlab check
worklog-hub gitlab sync --from 2026-10-01 --to 2026-10-31
worklog-hub sync-status
```

Диапазон `--from` / `--to` включительный. `spent_at` хранится в UTC, а исходная
календарная дата списания — отдельно в `spent_date`.

Для обычного пользователя GitLab timelogs запрашиваются отдельно по доступным
группам и проектам, потому что общий запрос без `groupId`, `projectId` или имени
текущего пользователя разрешён только администраторам. Результаты объединяются
по внешнему ID, поэтому пересечение групп и проектов не создаёт дублей.

Команда `gitlab sync` каждый раз синхронизирует полный доступный каталог GitLab,
а затем timelogs заданного периода. Собираются только группы и проекты, в которых
пользователь токена состоит участником, и только видимые ему сущности. Итерации
и эпики зависят от редакции, лицензии и версии конкретного GitLab.

Каталог хранится в таблицах `groups`, `projects`, `users`, `memberships`,
`work_items`, `branches` и `iterations`. Issues, tasks, merge requests и эпики
используют общую таблицу `work_items` с различным значением `kind`. Исходный JSON
сохраняется для групп, проектов, пользователей, членства, work items и итераций.

## Повторная сверка

Сначала клиент полностью получает все страницы заданного периода. Только после
успеха данные записываются транзакцией, а локальные GitLab-записи, которых больше
нет в полной выборке этого периода, удаляются. Ошибка сети или пагинации не
удаляет ранее загруженные данные.

Каталог также загружается со всей пагинацией. При успешной полной загрузке
сущности, которых больше нет в доступной выборке, не удаляются физически, а
помечаются неактивными. Это сохраняет историю и внешние связи.

Если отдельный тип каталога недоступен из-за роли пользователя, лицензии или
версии GitLab, синхронизация продолжает работу и записывает предупреждение.
Такой раздел считается неполным: ранее сохранённые строки этого типа не
помечаются неактивными. Ошибки подключения, авторизации самого токена и
пагинации остаются фатальными.

## Миграции и тесты

SQL-миграции применяются автоматически при первой команде, работающей с базой.

```powershell
uv sync --group dev
uv run python -m unittest discover -v
```

Проверка линтером и форматтером Ruff:

```powershell
uv run ruff check .
uv run ruff format --check .
```

## Jira

Сетевой код Jira намеренно не реализован. Для следующего этапа нужны
обезличенные примеры из DevTools: URL, HTTP-метод, значимые заголовки (без
cookie и токенов), параметры запроса и JSON-ответы. Проект не будет обходить
SSO, авторизацию или ограничения доступа.
